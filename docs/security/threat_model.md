# نموذج التهديدات (Threat Model)

هذا الملف يحلّل التهديدات الأمنية الرئيسية لتطبيق Avahi (متعدد المستأجرين،
Offline-First، عامل ميداني عبر متصفح ويب مشترك أحياناً) والتخفيفات
المُطبَّقة فعلياً في الكود لكل تهديد.

## 1. تسرّب بيانات بين المستأجرين (Tenant Data Leakage)

**التهديد**: مستخدم في الشركة A يرى بيانات الشركة B (الأخطر في نظام متعدد
المستأجرين).

**التخفيف**:
- عزل صارم على مستوى قاعدة البيانات عبر RLS (`company_id =
  auth.user_company_id()`) لكل استعلام، بصرف النظر عن منطق الواجهة —
  انظر [rls_policies.md](./rls_policies.md). حتى لو احتوى كود Flutter على
  خطأ يطلب بيانات شركة أخرى بالخطأ، Postgres يرفض إرجاعها.
- `auth.user_company_id()` مبنية على عضوية **نشطة واحدة فقط** (`is_active =
  true`)، فتعطيل عضوية مستخدم يقطع وصوله فوراً بلا حاجة لحذف حسابه.
- الاستثناء الوحيد الموثَّق (`auth.is_platform_owner()`) محصور بجدول
  `platform_admins` منفصل تماماً، لا يُدار إلا من مالكي المنصة أنفسهم.

## 2. تصعيد الصلاحيات (Privilege Escalation)

**التهديد**: مستخدم بدور `worker` يعدّل طلب HTTP مباشرة (متجاوزاً واجهة
Flutter) لتنفيذ عملية مخصصة لأدوار أعلى (مثال: حذف مهمة، اعتماد حضور).

**التخفيف**:
- كل سياسة RLS تتحقق من الدور عبر `auth.has_min_role(...)` **في قاعدة
  البيانات نفسها**، مقروءاً من `company_members.role` — عمود لا يتحكم به
  العميل مباشرة (تعديله يتطلب صلاحية `admin` فأعلى أصلاً، انظر سياسة
  `company_members_update`).
- `RolePermissions.map` في Flutter (`core/constants/permissions.dart`)
  موثَّقة صراحة كطبقة واجهة فقط، **غير موثوق بها أمنياً وحدها** — أي مطوّر
  يضيف صلاحية جديدة مُلزَم بإضافة سياسة RLS مطابقة (انظر تنبيه
  [roles_matrix.md](./roles_matrix.md)).
- تغيير دور مستخدم (`usersEditRoles`) محصور بـ `admin` فأعلى على مستوى
  RLS أيضاً (`company_members_update`)، لا فقط زر مخفي في الواجهة.

## 3. انتحال هوية عبر JWT مزوَّر أو منتهي الصلاحية

**التهديد**: طلب يحمل رمز JWT مزوَّر أو منتهي الصلاحية يصل إلى Edge
Function أو PostgREST مباشرة.

**التخفيف**:
- كل Edge Function (`backend/supabase/functions/`) تتحقق من الرمز عبر
  `supabaseAdmin.auth.getUser(jwt)` (`_shared/auth.ts`) الذي يتحقق من
  توقيع الرمز عبر GoTrue مباشرة قبل تنفيذ أي منطق حسّاس — لا وثوق بأي
  ادّعاء هوية غير موقّع من الخادم.
- PostgREST (الطبقة التي يتحدث معها `supabase_flutter` مباشرة) يتحقق من
  توقيع JWT تلقائياً ضمن طبقة Supabase نفسها قبل تمرير الطلب لـ Postgres،
  حيث تُطبَّق RLS بعدها بمعزل تام.

## 4. تسجيل حضور مزوَّر جغرافياً (GPS Spoofing) / حضور مكرر

**التهديد**: عامل يزوّر إحداثيات GPS لتسجيل حضور من خارج موقع المشروع
فعلياً، أو يحاول تسجيل حضور مزدوج (خطأ شبكة/إعادة إرسال).

**التخفيف**:
- التحقق من نطاق `geofence_radius_meters` يُنفَّذ من طرف الخادم (Edge
  Function `attendance-guard`)، لا يُكتفى بحساب المسافة محلياً في Flutter
  فقط (الذي يمكن التلاعب به على جهاز مُروَّض/Rooted).
- `attendance.client_mutation_id` **UNIQUE** على مستوى قاعدة البيانات يمنع
  حضوراً مكرراً من نفس عملية Outbox حتى مع إعادة إرسال متعددة بسبب مشاكل
  شبكة.
- `attendance_insert` RLS تسمح فقط بتسجيل حضور لنفس المستخدم
  (`user_id = auth.uid()`) — لا يمكن لعامل تسجيل حضور نيابة عن زميله عبر
  هذا المسار مباشرة، حتى مع تعديل الحمولة يدوياً.
- محلل تعارض `FirstWriteWinsResolver` (انظر
  [03_sync_strategy.md](../architecture/03_sync_strategy.md)) يمنع Race
  Condition عند محاولتي تسجيل من جهازين لنفس المستخدم.

## 5. بيانات حساسة مخزَّنة محلياً على جهاز مشترك/مفقود

**التهديد**: جهاز (لوحي/حاسوب) يُستخدَم من عدة عمال بالتناوب، أو يُفقَد،
ويحوي بيانات محلية (Drift) لجلسة سابقة.

**التخفيف**:
- رمز الجلسة (JWT/Refresh Token) يُخزَّن عبر `flutter_secure_storage`
  (تشفير مستوى نظام التشغيل)، لا `shared_preferences` العادي.
- `PinHasher` يستخدم SHA-256 لتخزين تجزئة رمز PIN المحلي (بوابة دخول سريعة
  على نفس الجهاز) بدل النص الصريح — موثَّق صراحة كآلية **محلية فقط** لا
  تُغني عن جلسة Supabase الفعلية خلفها.
- `SettingsCubit`/`SessionService` توفّر تسجيل خروج كامل يمسح كل من الجلسة
  السحابية والبيانات المحلية الحساسة (Drift + Secure Storage) — يُوصى
  تشغيلياً بتفعيله دوماً عند تبديل عامل لآخر على نفس الجهاز المشترك (انظر
  [docs/user_manuals/field_worker_guide_ar.md](../user_manuals/field_worker_guide_ar.md)).

## 6. حذف/تلاعب بسجل التدقيق (Audit Log Tampering)

**التهديد**: مستخدم (حتى `admin`) يحاول حذف أو تعديل سجل تدقيق لإخفاء أثر
عملية معينة.

**التخفيف**:
- لا توجد سياسة RLS من نوع `insert`/`update`/`delete` للمستخدمين العاديين
  على جدول `audit_logs` إطلاقاً — الكتابة الوحيدة الممكنة عبر Trigger
  بصلاحية `security definer` ([017_audit_triggers.sql](../../backend/supabase/migrations/017_audit_triggers.sql)).
  حتى `admin` لا يملك صلاحية تعديل السجل يدوياً، فقط قراءته.

## 7. رفع ملفات ضارة (Malicious File Upload)

**التهديد**: رفع ملف بامتداد تنفيذي أو حجم مفرط عبر `documents`/`photos`.

**التخفيف**:
- `file_picker`/`image_picker` في العميل يقيّدان أنواع الملفات المقبولة
  استباقياً، و`ImageCompressor` يضغط الصور قبل الرفع.
- Supabase Storage buckets مهيّأة بحدود حجم وأنواع MIME مسموحة على مستوى
  الخادم (`backend/supabase/config.toml`) — القيد الفعلي دوماً خادمي، لا
  عميلي فقط.
- لا تُنفَّذ أي ملفات مرفوعة على الخادم مباشرة (تخزين خام فقط، لا معالجة
  تنفذ محتوى الملف)، مما يلغي خطر تنفيذ كود عن بعد عبر رفع ملف.

## 8. هجمات حجب الخدمة عبر المزامنة (Sync Flooding)

**التهديد**: خلل في العميل (أو تلاعب متعمد) يُغرق الخادم بطلبات مزامنة
متكررة.

**التخفيف**:
- `ExponentialBackoff` + `RetryPolicy` (`data/sync/retry/`) يحدّان تلقائياً
  من معدل إعادة المحاولة عند تكرار الفشل.
- فترات `ContinuousSyncStrategy` تزداد تحفظاً في بيئات أعلى (دقيقة واحدة
  `dev`، 5 دقائق `prod`) لتقليل الحمل التراكمي عبر آلاف المستخدمين.
- `IdempotencyHelper` (`clientMutationId`) يمنع تكرار نفس العملية عدة مرات
  في الطابور من الأساس.

## 9. تصدير بيانات مستأجر غير مصرَّح به

**التهديد**: استخدام ميزة تصدير بيانات المستأجر (`platform_admin`،
Edge Function `export-tenant-data`) من طرف غير مالك منصة.

**التخفيف**:
- `Permission.platformExportTenantData` ممنوحة حصراً لـ `platformOwner`
  في `RolePermissions.map`، وتقابلها في `export-tenant-data/index.ts`
  تحقق صريح عبر `_shared/auth.ts` من `auth.is_platform_owner()` قبل تنفيذ
  أي استعلام تصدير — رفض فوري (`403`) لأي طلب من غير مالك منصة، بصرف النظر
  عن حالة واجهة العميل.

## نطاقات خارج تغطية هذا النموذج (حدود موثَّقة صراحة)

- أمان البنية التحتية لاستضافة Supabase نفسها (مسؤولية Supabase Cloud أو
  فريق DevOps عند الاستضافة الذاتية عبر `docker-compose.yml`).
- هجمات على مستوى المتصفح غير مرتبطة بالتطبيق (إضافات متصفح ضارة، أجهزة
  مصابة ببرمجيات تجسس تسجل ضغطات لوحة المفاتيح).
- هندسة اجتماعية (Social Engineering) لخداع مستخدم شرعي لمشاركة بيانات
  دخوله طوعاً.
