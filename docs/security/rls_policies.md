# سياسات RLS (Row Level Security)

كل جدول بيانات (باستثناء `platform_admins`) محمي بسياسات RLS مُفعَّلة في
Postgres عبر Supabase — لا استثناءات ولا اعتماد على منطق الواجهة وحده. هذا
الملف يوثّق المنطق الكامل المُطبَّق في
[`016_rls_policies.sql`](../../backend/supabase/migrations/016_rls_policies.sql)،
بالاستناد لدوال المساعدة في
[`015_rls_helper_functions.sql`](../../backend/supabase/migrations/015_rls_helper_functions.sql).

## المبدأ العام

كل سياسة تتبع نفس الصيغة الأساسية:

```sql
(company_id = auth.user_company_id() and <شرط دور/ملكية إضافي>)
or auth.is_platform_owner()
```

أي: **العزل الصارم بين المستأجرين هو القاعدة المطلقة**، ولا يُتجاوَز إلا من
`platform_admins` (مالك المنصة). ضمن الشركة نفسها، تُضاف شروط دقيقة بحسب
الدور (`auth.has_min_role(...)`) أو الملكية الشخصية للسجل (`user_id =
auth.uid()` / `created_by = auth.uid()` / `assigned_to = auth.uid()`).

## دوال المساعدة (`auth.*`)

| الدالة | الغرض |
|---|---|
| `auth.user_company_id()` | `company_id` الخاص بعضوية المستخدم النشطة الحالية |
| `auth.user_role()` | نص الدور الحالي (`worker`..`admin`) |
| `auth.is_platform_owner()` | هل المستخدم مسجَّل في `platform_admins`؟ |
| `auth.role_rank(role_name)` | يحوّل اسم الدور لترتيبه الرقمي (يطابق `UserRole.rank` في Dart تماماً) |
| `auth.has_min_role(min_role)` | هل رتبة المستخدم ≥ `min_role`، أو مالك منصة؟ |
| `auth.is_project_member(project_id)` | هل المستخدم عضو نشط في مشروع محدد؟ |

كل هذه الدوال `security definer` لتفادي التكرار اللانهائي (Recursive RLS)
عند قراءتها لجدول `company_members` نفسه المحمي بسياساته الخاصة.

## سياسات كل جدول

### `companies`
- **قراءة**: عضو الشركة أو مالك منصة.
- **تعديل**: `admin` فأعلى ضمن الشركة، أو مالك منصة.
- **إنشاء/حذف**: مالك منصة فقط (الشركات تُنشأ عبر Edge Function
  `create-company`).

### `company_members`
- **قراءة**: عضو الشركة نفسها.
- **إضافة عضو**: `admin` فأعلى، أو مالك منصة.
- **تعديل**: `admin` فأعلى، **أو المستخدم نفسه** (تحديث بياناته الشخصية).
- **حذف**: `admin` فأعلى.

### `projects`
- **قراءة**: أي عضو نشط في الشركة.
- **إنشاء/تعديل**: `projectManager` فأعلى.
- **حذف (أرشفة)**: `admin` فأعلى.

### `project_members`
- **قراءة**: أي عضو في الشركة.
- **كل الكتابة (`for all`)**: `projectManager` فأعلى.

### `tasks`
- **قراءة**: أي عضو في الشركة (تُفلتَر لاحقاً في الواجهة بحسب `assigned_to`
  لدور `worker`، لكن RLS لا تمنع القراءة العامة ضمن الشركة).
- **إنشاء**: `engineer` فأعلى.
- **تعديل**: `engineer` فأعلى، **أو الشخص المُسنَد إليه المهمة** (تحديث
  حالتها/تقدّمها).
- **حذف**: `projectManager` فأعلى.

### `attendance` — الأكثر حساسية
- **قراءة**: **صاحب السجل نفسه**، أو `foreman` فأعلى.
- **إنشاء (تسجيل حضور)**: **فقط لنفس المستخدم** (`user_id = auth.uid()`) —
  لا يمكن لأي مستخدم تسجيل حضور نيابة عن آخر مباشرة عبر هذا المسار.
- **تعديل (تسجيل انصراف/اعتماد)**: صاحب السجل، أو `foreman` فأعلى (للاعتماد
  والرفض).
- **حذف**: `admin` فأعلى فقط.
- انظر أيضاً القيد `attendance_client_mutation_id_unique` (فريد على مستوى
  قاعدة البيانات) الذي يمنع تسجيل حضور مكرر من نفس عملية Outbox — طبقة
  حماية إضافية مستقلة عن RLS نفسها.

### `field_reports`
- **قراءة**: صاحب التقرير، أو `foreman` فأعلى.
- **إنشاء**: بواسطة منشئه فقط (`created_by = auth.uid()`).
- **تعديل**: صاحب التقرير **طالما لا يزال `draft`**؛ بعد التقديم، فقط
  `engineer` فأعلى (للاعتماد/الرفض) — منع تعديل تقرير بعد تقديمه من قِبل
  منشئه لضمان مصداقية سجل المراجعة.
- **حذف**: صاحب التقرير طالما `draft`، أو `projectManager` فأعلى.

### `punch_items`
- **قراءة**: أي عضو في الشركة.
- **إنشاء**: أي عضو نشط (`worker` فأعلى — أي الجميع).
- **تعديل**: الشخص المُسنَد إليه، أو منشئها، أو `foreman` فأعلى.
- **حذف**: `engineer` فأعلى.

### `photos`
- **قراءة**: أي عضو في الشركة.
- **إنشاء**: من رفعها فقط (`uploaded_by = auth.uid()`).
- **حذف**: من رفعها، أو `projectManager` فأعلى.
- (لا سياسة `update` صريحة — الصور غير قابلة للتعديل بعد الرفع، فقط
  حذف/إعادة رفع.)

### `documents`
- **قراءة**: أي عضو في الشركة.
- **إنشاء/تعديل**: `engineer` فأعلى.
- **حذف**: `projectManager` فأعلى.

### `equipment`
- **قراءة**: أي عضو في الشركة.
- **إنشاء**: `projectManager` فأعلى.
- **تعديل**: `projectManager` فأعلى، أو الشخص المُعيَّنة له المعدة حالياً
  (تحديث ساعات الاستخدام مثلاً).
- **حذف**: `admin` فأعلى.

### `notifications`
- **قراءة/تعديل/حذف**: **المستلم فقط** (`user_id = auth.uid()`) — عزل
  صارم حتى داخل نفس الشركة.
- **إنشاء**: `foreman` فأعلى (من يملك صلاحية إرسال إشعار لعضو فريق)، أو عبر
  Edge Functions بصلاحية `service_role` (تتجاوز RLS للإشعارات النظامية
  التلقائية مثل `equipment-alert`/`leave-request-notify`).

### `leave_requests`
- **قراءة**: صاحب الطلب، أو `foreman` فأعلى.
- **إنشاء**: بواسطة صاحب الطلب فقط.
- **تعديل**: صاحب الطلب طالما `pending` (للإلغاء)، أو `foreman` فأعلى
  (للاعتماد/الرفض).
- **حذف**: `admin` فأعلى.

### `audit_logs`
- **قراءة**: `admin` فأعلى فقط.
- **لا توجد سياسة `insert`/`update`/`delete` صريحة للمستخدمين** — الكتابة
  الوحيدة الممكنة هي عبر دالة Trigger بصلاحية `security definer`
  ([017_audit_triggers.sql](../../backend/supabase/migrations/017_audit_triggers.sql))،
  ما يضمن استحالة تلاعب أي مستخدم (حتى `admin`) بسجل التدقيق مباشرة.

### `platform_admins`
- **قراءة/كتابة**: مالك منصة فقط — الجدول الوحيد بلا أي عزل `company_id`
  (لأنه أساساً يقع فوق مستوى الشركات).

## علاقة السياسات بـ `RolePermissions` في Flutter

كل صف في [roles_matrix.md](./roles_matrix.md) له سياسة RLS مقابلة هنا
بنفس الحد الأدنى من الدور تماماً. مثال: `Permission.tasksCreate` ممنوحة
لـ `engineer` فأعلى في `RolePermissions.map`، وتقابلها `tasks_insert`
بشرط `auth.has_min_role('engineer')` — أي اختلاف بين الاثنين يجب اعتباره
عيباً (Bug) يُصلَح فوراً في كلا الطرفين معاً.
