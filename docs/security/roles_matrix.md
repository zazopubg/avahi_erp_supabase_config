# مصفوفة الأدوار والصلاحيات (Roles Matrix)

المصدر الوحيد للحقيقة لهذه المصفوفة هو `lib/core/constants/permissions.dart`
(`RolePermissions.map`) على مستوى Flutter، ومطابق تماماً بدالة
`auth.has_min_role()`/سياسات RLS الصريحة على مستوى Postgres
(`backend/supabase/migrations/016_rls_policies.sql`). أي تعديل مستقبلي على
هذه المصفوفة **يجب** أن يُطبَّق في كلا الموضعين معاً؛ اختلاف الاثنين هو
ثغرة أمنية (الواجهة تُخفي زراً لكن قاعدة البيانات تسمح بالعملية، أو العكس).

## ⚠️ تنبيه معماري مهم

خريطة `RolePermissions.map` في Flutter **مرجعية لواجهة المستخدم فقط**
(إظهار/إخفاء أزرار وشاشات استباقياً لتجربة أفضل). **التحقق الملزم الفعلي
الوحيد** هو سياسات RLS في Supabase — لا يُعتمَد على فحص الواجهة كخط دفاع
أمني، لأن أي عميل يمكن تعديله أو التحايل عليه (DevTools، طلب HTTP مباشر).

## ترتيب الأدوار (من الأقل إلى الأعلى صلاحية)

`worker` (0) → `foreman` (1) → `engineer` (2) → `projectManager` (3) →
`admin` (4) → `platformOwner` (5)

`admin` يملك كل الصلاحيات ضمن حدود شركته فقط (باستثناء صلاحيات إدارة
المنصة). `platformOwner` يملك كل الصلاحيات دون استثناء، عابرة لكل
المستأجرين (`auth.is_platform_owner()`).

## ملاحظات تصميم

- **الفصل بين "الدور" (`UserRole`) و"الصلاحية" (`Permission`)**: الدور يحدد
  **من** هو المستخدم، بينما الصلاحية تحدد **ماذا** يمكنه فعله فعلياً. هذا
  يسمح مستقبلاً بمنح صلاحية استثنائية لمستخدم واحد دون تعديل نظام الأدوار
  بأكمله (غير مُفعَّل حالياً؛ الخريطة اليوم 1:1 بين دور ومجموعة صلاحيات
  ثابتة).
- **`admin` مستوى مستأجر واحد فقط**: مدير النظام لا يرى بيانات شركات أخرى
  إطلاقاً (RLS تفرض `company_id = auth.user_company_id()` بصرف النظر عن
  الدور) — فقط `platformOwner` يتجاوز هذا القيد عبر
  `auth.is_platform_owner()`.
- انظر [threat_model.md](./threat_model.md) لتحليل التهديدات المرتبطة
  بتصعيد الصلاحيات (Privilege Escalation) وكيف تمنعه هذه المصفوفة مقترنة
  بـ RLS.
